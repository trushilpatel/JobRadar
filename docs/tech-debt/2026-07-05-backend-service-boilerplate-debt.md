## P0 — Structural (boilerplate, primary focus of this audit)

- [x] **CRUD decode-or-400 boilerplate copy-pasted ~20+ times, no shared helper** — identical `json.NewDecoder(r.Body).Decode(&x); if err != nil { handler.RespondError(...); return }` block in `CompanyAdminRestService.go` (4×), `JobRestService.go` (5×), `applyqueue`'s `setResume`, `ApplicationRestService.go` (4×), `AtsRestService.go`, `UserRestService.go`/`UserAdminRestService.go` (7×). Fixed 2026-07-05: added `handler.DecodeBody[T](w, r) (T, bool)` to `apps/api/handler/respond.go` (writes a 400 BAD_REQUEST itself on failure, returns `(zero, false)`), with 4 new unit tests (valid, malformed JSON, empty body, shape-mismatch). Migrated all 20+ call sites across 11 `RestService` files: `application`, `company` (admin), `job`, `applyqueue`, `ats`, `user` (self-service + admin), `scan`, `pipeline`, `crawlernode` (node-facing + admin). Two deliberate exceptions kept hand-rolled: (1) `JobRestService.go`'s `dismiss` — DELETE may carry an empty body, decode failure silently defaults `Reason` rather than 400ing, a _different_ semantic than "decode or reject" so `DecodeBody` doesn't fit; (2) `crawlernode`'s two REST files previously round-tripped decode failures through `domainerrs.ErrBadRequest.WithMessage(...)` + `handler.HandleError` — traced through `HandleError`'s logic and confirmed this produces an identical client-visible response (400/BAD_REQUEST, generic message; the appended `err.Error()` detail was only in `InternalMessage`, which `HandleError` never logs for 4xx) — safe to migrate, and migrated. Anonymous inline `struct{...}` request bodies were promoted to named types (`setSavedRequest`, `setAllActiveRequest`, `updateScanIntervalOverrideRequest`) for readability at the `DecodeBody[T]` call site. Full backend `gofmt`/`build`/`vet`/`golangci-lint`/`go test -race`/coverage-gate all clean afterward. `resume/` still excluded (has the same pattern in `ResumeRestService.go` — another agent has that slice in progress).
- [x] **Bare unwrapped `return err` sites lose call-site context** — `JobRepositoryService.go` (8 sites), `ApplicationRepositoryService.go` (6 sites, excl. 2 that already returned a well-formed `ErrBadRequest`), `AtsCacheService.go` (3), `ScanImplService.go` (1), `ScanLogRepositoryService.go` (9). Fixed 2026-07-05: wrapped each with `fmt.Errorf("<pkg>.<method>: %w", err)`. **Correction to the original framing:** this is _not_ "3 incompatible conventions to converge onto 1." Re-investigated against `common/errors/CLAUDE.md` and `apps/api/handler/respond.go`'s `HandleError` (`errors.As` walks the `Unwrap()` chain): (1) the repo/terminal layer legitimately returns raw DB errors bare so `domain.IsNotFound()`-style checks work upstream (e.g. `JobImplService.go:228` converts `GetJobByID`'s raw `gorm.ErrRecordNotFound` into `ErrNotFound.WithMessage(...)` — this is intentional layering, not a bug) — `fmt.Errorf(...%w...)` is _additive_ here (adds context, preserves the `Is`/`As` chain), not a competing convention; (2) `domainerrs.Err*.WithMessage(...)` string-concat is the **documented, correct** pattern for returning a sentinel `*ServiceError` that `handler.HandleError` inspects — it does not need to preserve `errors.Is/As` on the wrapped raw error because only the `ServiceError`'s own `Code` is compared, never the underlying cause. Only the genuinely bare, zero-context `return err` sites were real defects; those are now fixed. No change made to the `WithMessage(...)` call sites — converging them onto `fmt.Errorf` would have been a regression (breaks `handler.HandleError`'s HTTP-status mapping for any sentinel that needs to survive to the handler). `resume/` excluded (another agent has it in progress).

## P1 — Structural

- [x] **Documented `toFetch*Response()` converter pattern used in only 2 of 12 slices** (`toATSDTO`, `toUserStateView`) — everywhere else DTOs built inline at call sites (`CrawlerNodeImplService.go:107-113,306-314`, `PipelineRepositoryService.go:98-118`, `ApplyQueueRepositoryService.go:210-224`). Fixed 2026-07-05 for `crawlernode`: extracted `toNodeView(n crawlernodemodel.CrawlerNode) dto.NodeView`, used by both `ProvisionNode` and `ListNodes` (previously duplicated the same shape with `Online` computed two different ways — `ProvisionNode` hardcoded `false`, `ListNodes` derived it from `LastSeenAt`; a freshly-created node's `LastSeenAt` is nil so both now compute the same result through one function). **Correction:** `pipeline/` and `applyqueue/` were re-examined and each has only **one** inline DTO-construction call site, not a repeated shape — extracting a named converter there wouldn't reduce duplication (there isn't any to reduce), it would just add an abstraction for a single call site, which `engineering-principles.md` explicitly warns against. Left as-is; not a real finding.
- [x] **`job/`'s caching folded into `ImplService` instead of the documented `CacheService` decorator** — `JobImplService.go:46,59,130,475-482` injects `cache.Cache` directly rather than extracting a `JobCacheService.go` mirroring `UserCacheService.go`. **Investigated 2026-07-05 and documented the deviation in `job/CLAUDE.md` instead of extracting** — this one is not just style: `List`'s cache entry holds the _pre-overlay_ global page (`s.jobs.GetJobs`'s raw result) before the per-user `user_job_state` overlay is merged in. A canonical outer `CacheService` decorator would instead cache `List`'s full return value with one user's overlay already merged in, which would then leak into a different user's cache hit on the same (cursor, filter) key — a real cross-user data leak, not a refactor. Extracting the decorator here would have been the wrong fix.
- [x] **Admin/worker wiring lives outside the slice's own `wire.go` for 3 of 12 slices** — `company/`, `user/` admin chains wired directly in `backend/apps/api/wire_gen.go`/`wire_multiuser.go`; `crawlernode/wire.go` has no `ProviderSet` at all, real wiring is manual in `backend/apps/orchestrator/main.go:83-113`. **Re-verified 2026-07-05 (follow-up session):** `company/` and `crawlernode/` were already false — `company/wire.go`'s `AdminProviderSet` and `crawlernode/wire.go`'s single `ProviderSet` both already list the real admin-chain constructors (this finding predated those). The one genuine gap was `user/` — its `wire.go` had no admin-chain entries at all. Fixed: added `user.AdminProviderSet` (mirroring `company/`'s pattern) listing `NewAdminRestRouter`/`NewAdminRestService`/`NewAdminValidationService`/`NewAdminImplService`/`NewAdminRepositoryService`, with a note that it's hand-wired in `apps/api/wire_multiuser.go`, not executed via Wire.
- [x] **"Validation" means 3 different things across slices** — pure field checks (`JobValidationService.go`, `CompanyValidationService.go`) vs. live DB authorization reads (`ApplyQueueValidationService.go:68-89`) vs. input mutation (`ResumeValidationService.go:40,49-52`). Fixed 2026-07-05 (follow-up session): added an explicit callout to `service/CLAUDE.md`'s `ValidationService` section naming all three semantics with their example files, so copying a slice's `ValidationService` as a template no longer silently assumes side-effect-free.
- [x] **`wire.go` constructor naming/ordering differs per slice** — bare `NewX` (`resume/`) vs. `NewApplicationX` vs. `NewPipelineX`; `scan/wire.go:9-17` lists providers in scrambled order vs. `ats/wire.go:17-24`'s clean top-down list. Fixed 2026-07-05 (user confirmed: do the cosmetic cleanup even though the ProviderSets are inert, see below): renamed `NewApplicationRestRouter`/`RestService`/`ValidationService`/`ImplService`/`RepositoryService` → bare `NewX` (5 sites + call sites in `apps/api/wire_gen.go`, `apps/api/app_test.go`, test files), same for `NewAtsX` → `NewX` (6 constructors) and `NewPipelineX` → `NewX` (5 constructors, kept `NewPipelineStore` — a distinct lower-level dependency, not a chain layer). Left `company/`'s `Admin` prefix and `crawlernode/`'s `Node`/`Assignment`/`Ledger`/`ScanLog`/`ScanSettings` prefixes alone — those disambiguate genuinely distinct multiple chains/repos in the same package, not redundant restatement of the package name. Reordered every slice's `ProviderSet` to top-down (`RestRouter → RestService → Validation → Cache → Impl → Repository`) for `ats/`, `audit/`, `crawlernode/`, `pipeline/`, `user/` (the rest already matched). `resume/` untouched throughout (another agent has it in progress). Full build + `go test ./...` clean after every rename.
  - **Bigger finding underneath this — resolved 2026-07-05 (follow-up session), docs-only per user decision:** every domain's `wire.go` `ProviderSet` is inert — running `wire`/`go generate ./apps/api/` against them fails with "multiple bindings" for the chain interface in **every** slice (`company` both chains, `scan`, `job`, `application`, `resume`, `applyqueue` all confirmed) because Wire's DI graph can't auto-resolve a chain of same-interface decorators without `wire.Bind` disambiguation (`wire.Bind` maps a concrete type to an interface it implements — it does not disambiguate _which of N providers of the same interface_ should feed a given consumer, which is what a decorator chain needs; confirmed by re-running `wire` in an isolated worktree). Presented the user two options — (a) docs-only fix now, or (b) the full refactor (one hand-written composing function per domain + real `go generate` regeneration of the whole `apps/api` DI graph, including the multi-user platform composition, intentional nil-cache paths, and the resume LLM-quota fallback logic) — user chose (a), correctly scoping the full regeneration out as its own separate, higher-risk piece of work (it touches live production API wiring end to end). Fixed: rewrote `apps/api/CLAUDE.md`'s `wire_gen.go` section to state the truth (hand-maintained, `go generate` fails, here's why, here's the real fix if someone takes it on) and propagated a short accurate NOTE to all 10 remaining domain `wire.go` files that didn't already have one (`pipeline/wire.go` already did). Also found in passing: `crawlernode/CLAUDE.md` claimed `wire.go` was "an empty stub" — false, it has a full (also-inert) 12-constructor `ProviderSet` since a 2026-06-24 fix populated it without updating this doc; fixed 2026-07-05 (first session). The full-regeneration refactor itself remains **not started** — a legitimate follow-up, scoped and understood, but its own PR.
- [x] **`scan/` carries a dummy no-op `SchedulerService` implementation alongside the real one** — `ScanRepositoryService.go:507-544` hardcodes 6 no-op methods each commented "never wired through the REST decorator chain"; real logic is in the unrelated `ScanSchedulerService.go` (474 lines), wired outside any decorator chain.
