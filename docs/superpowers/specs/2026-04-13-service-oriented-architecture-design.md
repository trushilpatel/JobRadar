# Service-Oriented Architecture Redesign

**Date:** 2026-04-13  
**Project:** JobRadar — backend  
**Status:** Approved, ready for implementation

---

## 1. Problem Statement

The current backend follows a `Handler → Store` pattern where handlers are fat — they contain validation logic, business logic, view assembly, and HTTP response writing all in one place. Pain points:

- Adapter validation duplicated across `Create` and `Update` in `companies.go`
- Business logic (e.g. `next_scan_at` computation, queue enrichment) lives in HTTP handlers
- Handlers hold 3–4 store interfaces directly — hard to test in isolation
- No consistent response envelope — success and error shapes are ad-hoc
- No typed filter structs — filters are raw `r.URL.Query().Get()` calls scattered in handlers

---

## 2. Goals

- Introduce a strict four-layer architecture per domain: **Handler → Validator → Service → Store**
- Standardize API responses with a discriminated typed envelope
- Add typed pagination and per-domain filter structs validated at the boundary
- Use **Google Wire** for compile-time dependency injection
- Keep the pipeline (`pipeline/`) untouched — only the API + store layers change

---

## 3. Architecture

### 3.1 Layer Responsibilities

| Layer | Responsibility | Must never |
|---|---|---|
| **Handler** | Parse HTTP input, call validator, call service, write envelope | Contain business logic or DB calls |
| **Validator** | Validate user-submitted input only (body, query params, URL params) | Make DB lookups or apply business rules |
| **Service** | Business logic, cross-service orchestration | Touch HTTP or raw GORM |
| **Store** | GORM queries for one domain's tables | Validate, apply business rules |

### 3.2 Data Flow

```
HTTP Request
    │
    ▼
Handler          ← parses body/query/path into typed input structs
    │
    ▼
Validator        ← validates user-submitted input (field presence, enums, formats)
    │              returns ValidationError on failure → handler responds 400
    ▼
Service          ← business logic; may call other services
    │              returns typed ServiceError (NOT_FOUND, CONFLICT, etc.) on failure
    ▼
Store            ← GORM queries; returns raw model or error
    │
    ▼
Handler          ← writes envelope response (Response[T], PagedResponse[T], ErrorResponse)
```

### 3.3 Service-to-Service Calls (allowed directions only)

```
DashboardService → JobService, InsightsService
ScanService      → CompanyService   (existence check + enrichment)
JobService       → (no upstream service calls)
ApplicationService → JobService     (job existence check)
```

No cycles. Import direction is always one-way.

## 5. Response Types

### 5.1 Success

```go
// Single resource
type Response[T any] struct {
    Data T `json:"data"`
}

// Paginated list (jobs, applications only)
type PagedResponse[T any] struct {
    Data  []T `json:"data"`
    Total int  `json:"total"`
    Page  int  `json:"page"`
    Limit int  `json:"limit"`
}
```

### 5.2 Errors

```go
type ValidationError struct {
    Field   string `json:"field"`
    Code    string `json:"code"`    // "REQUIRED", "INVALID_VALUE", "TOO_LONG"
    Message string `json:"message"`
}

type ServiceError struct {
    Code    string // "NOT_FOUND", "CONFLICT", "BAD_REQUEST", "INTERNAL"
    Message string
    Status  int    // HTTP status code
}

// Sentinel errors
var (
    ErrNotFound   = &ServiceError{Code: "NOT_FOUND",   Status: 404}
    ErrConflict   = &ServiceError{Code: "CONFLICT",    Status: 409}
    ErrBadRequest = &ServiceError{Code: "BAD_REQUEST", Status: 400}
    ErrInternal   = &ServiceError{Code: "INTERNAL",    Status: 500}
)

// Wire message onto a sentinel:
// return response.ErrNotFound.WithMessage("company not found")
```

Wire format on the wire:
```json
{ "error": { "code": "NOT_FOUND", "message": "company not found" } }
```

### 5.3 Handler error mapping

```go
func handleError(w http.ResponseWriter, err error) {
    var vErr *response.ValidationError
    if errors.As(err, &vErr) {
        RespondError(w, 400, vErr.Code, vErr.Message)
        return
    }
    var sErr *response.ServiceError
    if errors.As(err, &sErr) {
        RespondError(w, sErr.Status, sErr.Code, sErr.Message)
        return
    }
    RespondError(w, 500, "INTERNAL", "unexpected error")
}
```

## 6. Pagination & Filters

### 6.1 Pagination (shared)

```go
// api/request/pagination.go
type Pagination struct {
    Page  int // default 1,  min 1
    Limit int // default 20, min 1, max 100
}

func ParsePagination(r *http.Request) Pagination // sets defaults if params absent
```

Validator always validates pagination when present:
- `page >= 1`
- `1 <= limit <= 100`

### 6.2 Per-Domain Filter Structs (user input, validated)

```go
// service/job/types.go
type JobFilter struct {
    Status  string `query:"status"`   // "new" | "saved" | "applied"
    Company string `query:"company"`  // company_id substring match
    Saved   *bool  `query:"saved"`
}

// service/company/types.go
type CompanyFilter struct {
    Active      *bool  `query:"active"`
    AdapterType string `query:"adapter_type"`
}

// service/scan/types.go
type QueueFilter struct {
    Status string `query:"status"` // "queued" | "processing"
    Source string `query:"source"` // "manual" | "scheduler"
}

// service/insights/types.go
type InsightsFilter struct {
    Days int `query:"days"` // default 30, min 1
}
```

### 6.3 Which endpoints get pagination

| Endpoint | Paginated |
|---|---|
| `GET /jobs` | Yes — `PagedResponse[Job]` |
| `GET /applications` | Yes — `PagedResponse[Application]` |
| `GET /companies` | No — plain `Response[[]CompanyView]` |
| `GET /companies/queue` | No — plain `Response[[]QueueEntryView]` |
| `GET /dashboard/*` | No — single stat object |
| `GET /insights/*` | No — aggregate results |

## 9. Typed Input Structs

All mutation inputs are typed structs — no `map[string]any`.

```go
// service/company/types.go
type CreateCompanyInput struct {
    ID          string `json:"id"`
    Name        string `json:"name"`
    URL         string `json:"url"`
    AdapterType string `json:"adapter_type"`
    Active      *bool  `json:"active"`
}

type UpdateCompanyInput struct {
    Name        *string `json:"name"`
    URL         *string `json:"url"`
    AdapterType *string `json:"adapter_type"`
    Active      *bool   `json:"active"`
}
// nil field = not provided = skip that column in UPDATE

// service/job/types.go
type DismissInput struct {
    Reason string `json:"reason"`
    Note   string `json:"note"`
}

type SetStatusInput struct {
    Status string `json:"status"`
}

type SetNotesInput struct {
    Notes string `json:"notes"`
}

// service/application/types.go
type CreateApplicationInput struct {
    Stage string `json:"stage"`

type UpdateStageInput struct {
    Stage string `json:"stage"`

type UpdateNoteInput struct {
    Note string `json:"note"`
```

## 10. Config Injection

Each service that needs config gets its own typed config struct — no service receives the global `config.Config` directly.

```go
// service/company/types.go
type Config struct {
    ScanIntervalMinutes int
}

// service/scan/types.go
type Config struct {
    ScanIntervalMinutes int
}
```

Wire providers in `cmd/api/wire.go`:
```go
func provideCompanyConfig(cfg *config.Config) company.Config {
    return company.Config{ScanIntervalMinutes: cfg.ScanIntervalMinutes}
}

func provideScanConfig(cfg *config.Config) scan.Config {
    return scan.Config{ScanIntervalMinutes: cfg.ScanIntervalMinutes}
}
```

## 11. Wire Setup

### Per-domain provider sets

```go
// service/company/wire.go
var ProviderSet = wire.NewSet(
    NewHandler,
    NewValidator,
    NewService,
    NewStore,
)
```

Same pattern in every domain package.

### Root injector

```go
// cmd/api/wire.go
//go:build wireinject

func InitializeApp(db *gorm.DB, cfg *config.Config) (*api.App, error) {
    wire.Build(
        provideCompanyConfig,
        provideScanConfig,
        company.ProviderSet,
        scan.ProviderSet,
        job.ProviderSet,
        application.ProviderSet,
        dashboard.ProviderSet,
        insights.ProviderSet,
        api.NewApp,
    )
    return nil, nil
}
```

Wire resolves the full graph at compile time. A missing provider = build failure, not a runtime panic.

## 12. Pipeline Store Migration

Pipeline workers currently import from `store/`. After this change they import from service domain packages for the store interfaces they need:

| Worker | Currently imports | After |
|---|---|---|
| `job_listing_crawler` | `store.ScanQueueStore`, `store.CompanyReader`, `store.SeenLedgerStore`, `store.CompanyScanLogWriter` | `scan`, `company` |
| `job_listing_relevance_filter` | `store.SeenLedgerWriter` | `job` |
| `job_post_analyzer` | `store.JobWriter`, `store.SeenLedgerWriter`, `store.SnapshotWriter` | `job` |
| `company_scan_scheduler` | `store.CompanyReader`, `store.ScanQueueStore` | `company`, `scan` |

Pipeline workers only use store interfaces — they never touch the service or handler layers. No circular dependency.

## 14. Testing Strategy

| Layer | Test type | What to fake |
|---|---|---|
| Handler | Unit | Fake Service + Validator via interface |
| Validator | Unit | No fakes — pure function on input |
| Service | Unit | Fake Store interfaces |
| Store | Integration | Real DB (testcontainers or test DB) |

Each domain's `*_test.go` files live alongside their source files within the domain package.

## 15. Migration Order (implementation sequence)

1. `api/response/` — shared response types + error types
2. `api/request/` — Pagination + ParsePagination
3. `service/company/` — full vertical slice (store → service → validator → handler)
4. `service/scan/` — depends on company service
5. `service/job/` — absorbs seen_ledger, discard, snapshot stores
6. `service/application/` — depends on job service
7. `service/insights/`
8. `service/dashboard/` — depends on job + insights services
9. `cmd/api/wire.go` — root Wire injector
10. Delete old `store/` files (except `errors.go`), delete old `api/handler/` files
11. Update pipeline worker imports to point at service domain packages
